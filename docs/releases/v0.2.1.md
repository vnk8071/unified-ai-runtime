# UAIRT 0.2.1: QNN through ONNX Runtime on Windows ARM64

A small release after 0.2.0. The C API and ABI are unchanged; the ONNX Runtime backend and the Python binding gained
plugin-device options, and the binding got a shutdown fix.

## What is new

- **`ep_device` for plugin execution providers.** ONNX Runtime's `onnxruntime-qnn` plugin exposes an NPU, a GPU and a CPU
  device under one `QNNExecutionProvider` name, and the old code appended the first match. On a Snapdragon laptop that could
  mean QNN's CPU backend without an error. `ep_device` accepts `auto` (default), `cpu`, `gpu` or `npu`; `auto` prefers an NPU,
  then a GPU, then a CPU, and all devices of the chosen type are passed to the provider. The error lists each device's type.
- **`AutoModel.from_file("model.onnx", device="npu")`** finds the `onnxruntime-qnn` Python package, registers its plugin and
  selects the NPU. On Windows its directory is added to the DLL search path, so the QNN libraries bundled with the wheel load.
  `ep_name` alone also finds the library for `QNNExecutionProvider`, `MLXExecutionProvider` and `WebGpuExecutionProvider`
  when their PyPI package is installed; explicit `ep_library` options still work without it.

```python
import uairt
model = uairt.AutoModel.from_file("rtmdet_qnn_ctx.onnx", device="npu")
print(model.options)  # ep_library=..., ep_name=QNNExecutionProvider, ep_device=npu
```

## What was verified, and what was not

`ctest` passes on macOS arm64 (Apple M5) with ONNX Runtime 1.24.4, and the Python tests pass. The `ep_device` validation and
the QNN auto-detection are covered by those tests. With `onnxruntime-ep-mlx` 0.31.1 and ONNX Runtime 1.31.1, `ep_device=gpu`
and `auto` placed all nodes of `tests/data/add_mul.onnx` on `MLXExecutionProvider` with byte-identical outputs to the CPU, and
`cpu`/`npu` were rejected with the device types the provider does have. With the `onnxruntime-ep-webgpu` 0.5.0 plugin,
`ep_device=gpu` and `auto` did the same on `WebGpuExecutionProvider` with ONNX Runtime 1.24.4.

The `edge-ai` pipeline was run through UAIRT with its `yolox_s.onnx` and `ep_name: MLXExecutionProvider` only: 20 frames,
an event written, exit 0, and raw output byte-identical to a direct ONNX Runtime MLX run (3 boxes, same classes). That run
found a shutdown segfault in the Python binding when an engine is left to `__del__`; it is fixed in this release.

A real QNN run through UAIRT was **not** done: the Windows route is based on the `edge-ai` project, which runs RTMDet and HRNet
pose on a Snapdragon X Elite NPU with the same plugin used directly, and no Snapdragon was available for this change. The Linux
`onnxruntime-qnn` plugin still cannot see the NPU; use the `qnn` backend there. See
[docs/backends/onnxruntime.md](../backends/onnxruntime.md).

## Compatibility

Python 3.9 and later; ONNX Runtime 1.22 or newer. The C API, the backend ABI and existing options are unchanged.
